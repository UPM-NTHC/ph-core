Note to Implementers: FHIR Capabilities

Any FHIR capability may be 'allowed' by the system unless explicitly marked as 'SHALL NOT'. A few items are marked as MAY in the Implementation Guide to highlight their potential relevance to the use case.

FHIR RESTful Capabilities

Mode: server

The PH Core Server SHALL support at least one relevant PH Core resource profile. Resource selection is optional; once selected for REST access, its listed profile, read, search and SHALL filters/combinations apply. Patient-centric exchange SHALL support PH Core Patient for the exchanged patient context; provider/facility directories need not implement Patient solely for Server conformance. Create and update remain optional. A Server declaring create SHALL support conditional create; a Server declaring update SHALL support conditional update and version-aware updates. The catalog's conditionalCreate, conditionalUpdate, versioning and transaction SHALL expectations have this documented applicability and do not require read-only Servers to implement writes. The minimum version policy is versioned; versioned-update also satisfies the requirement. Write-enabled ingestion means create or update is supported for at least one selected PH Core resource; such Servers SHALL support atomic transaction Bundles for their supported resources. Servers SHALL support GET and POST search, paging, _count and the search semantics and combinations specified in Client and Server conformance. Servers SHALL return conformant JSON, enforce authorization, and fulfill profile constraints and applicable actor obligations. They SHALL publish an implementation-specific kind=instance CapabilityStatement at GET [base]/metadata, use instantiates for this requirements statement, and declare their actual selected PH profiles, supported interactions, conditional/versioning policies, searches, joins, operations, formats and security arrangements. They SHOULD identify conforming profiles in meta.profile. A dual-role implementation MAY instantiate both PH requirements statements with client and server REST blocks. Profile-only conformance does not require the REST contract. Supporting a profile or search does not mandate a program workflow or new data capture.

Security

The Server SHALL use HTTPS for production exchange, apply deployment authorization/consent policies and reject unauthorized requests using appropriate FHIR responses. Invalid requests, unknown resources and insufficient authorization SHALL produce appropriate 400, 404 and 401/403 responses, subject to FHIR security behavior. OperationOutcome content SHALL follow FHIR rules. Deployment or downstream guides SHALL define authentication, authorization, consent, trust and audit arrangements.

Summary of System-wide Interactions
  • SHALL support the transactioninteraction described as follows:

    Required only for write-enabled ingestion Servers, meaning create or update is supported for a selected PH Core resource. Read-only Servers may omit transaction. Supported resource entries SHALL be processed atomically with conditional-create/update semantics, temporary fullUrl reference resolution and a transaction-response. Unsupported or failing entries SHALL fail the transaction without partial persistence.

  • MAY support the batchinteraction described as follows:

    Batch support is optional and does not provide the atomicity of a transaction.

  • MAY support the history-systeminteraction described as follows:

    System history is optional; deployments needing deletion-aware synchronization SHALL define an appropriate history/tombstone or equivalent contract.

  • MAY support the search-systeminteraction described as follows:

    Cross-resource system search is optional; the baseline requires resource-type search for selected resources.
